# Activity filters and map usability

The web shares one explicit activity selection between the activity list and map tracks: inclusive `date_from`/`date_to` ISO calendar dates, exact case-insensitive trimmed `activity_type` (80 characters maximum), and `source=all|gpx|fit|unknown`. Empty dates/type mean no restriction. Unknown/invalid activity dates remain visible without date restrictions and are excluded when either date bound is supplied. `unknown` activity type covers empty/null/unknown metadata. Unknown source means an activity with no attached owner source; unsupported future providers are not advertised. Multiple matching sources never duplicate activities or GPS nodes. Original metadata, GPS samples and timestamps are unchanged.

`GET /api/activities` retains search/paging and its exact default response shape, adding these optional query filters before totals, sorting and paging. `GET /api/activities/filters` returns owner-scoped normalized `activity_types` (sorted, bounded to 100) and `types_truncated`. This literal route must precede the activity-ID route. Validate calendar inputs and reversed dates with safe 422s. SQLite default activity tests remain compatible; source-filter tests supply a synthetic source table.

`GET /api/map` and `GET /api/progress` accept the same filters and `coverage_scope=lifetime|filtered` (default lifetime). Tracks always follow the selected activity filters. Lifetime coverage, missing nodes and counts continue to use all retained GPS support. Filtered coverage uses only current successful matching source contributions from selected activities and, when a source kind is selected, only that matching source kind. It is coverage recorded within the selection, not new-node gains or the historical snapshot at the end date. It never scans/simplifies tracks to fabricate visits. Manual labels remain lifetime annotations; they never complete streets or remove missing nodes in filtered GPS coverage. The backend echoes canonical `filters` and `coverage_scope` in map/progress responses, with backwards-compatible schema defaults; default clients/fixtures continue to work.

Both coverage scopes retain the existing account-wide conservative pending/failed matching gates, independent of activity selection. `pending_imports` remains account-wide and informational: queued/unparsed uploads do not themselves turn existing ready coverage into null totals. They have no known date yet, so the UI displays their processing count separately. Both scopes preserve exact current source/revision/dataset/successful run/job provenance, repeatable-read snapshots, existing viewport/output limits and the 1.5-second per-statement query timeout. Region denominators are unchanged. Eligible streets/nodes and visited/completed metrics stay unavailable while matching is pending/failed. Per-dataset filtered visited-node/unsupported-sample diagnostics come from selected qualified contributions/runs. Global `unmapped_points` is the sum for selected activities; with default filters its existing lifetime behavior is unchanged. City/street browse and per-run historical contribution comparisons remain lifetime views and say so explicitly.

The shared client waits for backend-generated types. Activity filter changes restart page one and clear old activity detail/impact; list pages and filter-option responses are fenced by account/request/filter selection. Map filter/scope changes invalidate both map/progress requests; late viewport, filter, scope, account and polling responses cannot publish stale data. Default API calls remain compatible. Unsupported response echoes fail safely rather than presenting lifetime data as filtered coverage. Imports, corrections, refresh and reconnect retain the selected filters/scope.

The web provides date/type/source controls with Apply/reset, visible selection and lifetime/selected-activity GPS coverage labels. Missing-node tools label filtered missing nodes as missing in the selection. A user's stored viewport contains only center/zoom, is validated and scoped to their account in local browser storage, and is restored after reload/sign-in. Account change/sign-out clears private map layers and uses that account's view or the public default; another account never inherits a previous account's location. No tracks or progress are persisted for offline use.

Current location is requested only by an explicit button, with finite/range validation, a marker, bounded timeout and useful denied/unavailable/timeout states. Late location callbacks after account change, cancellation, unmount or a newer request do nothing. The location is not an activity, waypoint, route request or GPS coverage visit.

Offline/connection-loss states say which data is stale/unavailable, disable stale map target actions, offer retry and refresh on reconnection. Network events and requests are account-fenced; reconnect cannot restore an old account or old filter selection. No native UI execution, provider connection, automatic routing, deployment, downloaded offline basemap or persistent private-data cache is part of this slice.
