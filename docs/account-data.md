# Account export and deletion (D32)

Scope: the implemented GPX/FIT account data, browser controls and shared client. No provider connection/sync, native UI, deployment or claim of legal retention compliance. D19's relevant source boundary is pinned here: original file provenance stays independent, no credentials are exported, and removing the account removes all its sources and derived support. Future provider retention policies require a separate contract before implementation.

## Export

`GET /api/account/export` requires the current bearer session and returns a private ZIP attachment (`city-runner-account.zip`, `application/zip`, `Cache-Control: no-store`). Use explicit export field allowlists. Include account ID/creation time, activities with unchanged segmented coordinates/aligned timestamps, GPX/FIT originals named by public source ID, source/status metadata, import manifests/items, source-node contributions/coverage run and summary metadata, manual labels and saved routes. JSON/NDJSON IDs are strings; a manifest records schema version, creation time, included entries/counts and scope. Exclude session/identity credentials, challenges, lease tokens, job payloads, internal storage keys and filesystem paths. No shared geography dump or provider-policy assumptions. Unknown unsupported source kinds fail explicitly rather than silently exporting prohibited data.

Copy a consistent owner snapshot to a private temporary ZIP while holding an exclusive owner guard against owner mutations and physical original cleanup. Acquire exclusive owner exclusion **before establishing the data snapshot**; do not establish a REPEATABLE READ snapshot in an advisory-lock query that can wait behind cleanup. Session exclusion followed by a repeatable-read transaction, or a stable owner view under READ COMMITTED exclusion, are valid. Stream records and original files with existing per-file bounds; cap uncompressed input at 2 GiB, final archive at 512 MiB, entries at 25,000 and elapsed construction at 120 seconds. Exceeding a limit gives a safe explicit error; missing originals fail the entire export, never a successful partial archive. Release the database/owner guard before streaming the completed file. Remove temporary artifacts on failure, completion and disconnect; they never become a retained account cache. Export and deletion requests for the same account serialize; other accounts remain usable.

## Owner fencing

Normal owner writes take a **shared** account advisory transaction guard before existing batch/job/source locks, preserving current same-account upload/retry/deletion interleavings. Export/account deletion use the exclusive counterpart. Use a stable namespaced owner key, recheck the account inside each mutation transaction, and reject deletion-ledger tombstones. Hold the guard before original creation and through ownership attachment or durable failure cleanup. Account existence/authentication checked before a request is insufficient.

Apply the guard to ingestion/matching/failure transactions, bulk create/attach/stop/resume/retry, activity deletion/manual labels, saved-route writes and actual original cleanup. Claim/lease-only job operations remain short; they cannot recreate account data. Auth retains identity-advisory-lock first, then account guard; deletion locks the account's existing identities in deterministic order before the exclusive owner guard and revalidates them. Signing in after completed deletion creates a new empty account with a new immutable ID; old tombstones never block that new account by provider subject.

## Deletion and storage

`DELETE /api/account` requires bearer auth and a typed body `{confirmation: "DELETE"}`; no caller-supplied account ID. Return 202 with `AccountDeletionResponse {id, status: "cleanup-pending"|"complete"}` only after independently durable deletion intent and committed removal of access/account data. The response explicitly distinguishes account removal from physical cleanup. An unauthenticated repeat gives 401; operator/worker replay of the same intent is idempotent. The browser offers explicit confirmation, clears only the captured session, discards owned stores/Files/viewport preference and states that originals are queued for removal. Replacement-account tokens/preferences must survive late export/delete responses. Account export or delete errors are actionable; deletion is not invoked automatically.

Keep an FK-independent `account_deletions` receipt/tombstone and per-object cleanup outbox, with bounded attempts/backoff, leases and lease/revision-safe acknowledgement. Capture current source object keys **and all pending/failed account `delete_private_object` job keys**, including already deleted activities, before removing account jobs. Explicitly delete activities (their current account FK does not cascade), and remove identities/sessions, sources/contributions/runs/summaries, routes/manual labels, batches/items and remaining owner jobs. Shared geography and other accounts are unchanged. No stale upload, worker, retry or authenticated write may recreate removed data.

New original writes durably record owner metadata in the private local object store before creating file bytes; use safe keys and an account-hash ownership directory. This permits cleanup of failed/unattached writes without guessing ownership or reading GPS contents. Capture these owned keys in deletion as well. Existing source rows and pending-cleanup job keys remain the migration compatibility path for older originals. Unlink the original and owner metadata, fsync their directories, then acknowledge cleanup. Missing files are idempotently successful. Failed cleanup is visible to operator status/retry, survives worker/API restart and never reports complete while objects remain. Keep receipt identity/timestamps only after successful cleanup; original keys may be purged from the DB outbox after independent restore protection exists.

## Independent ledger and restore

Configure `ACCOUNT_DELETION_LEDGER` as a separately retained private append-only local journal; initialize it explicitly for a fresh installation. D32 deletion is unavailable without configuration. When configured, missing/unreadable/corrupt ledger fails closed for auth/owner mutations and account operations. Legacy unconfigured installations preserve existing APIs while the new deletion endpoint explains missing configuration. Journal records contain only immutable old account IDs, deletion request IDs/time and captured random original keys, never GPS or credentials. Protect it with 0600 permissions, symlink-safe opens and file/directory fsync.

While holding owner exclusion, fsync the full deletion intent **before destructive DB changes**. That is the irreversible commit point. Any later DB/HTTP failure rolls forward through worker/CLI replay; do not claim it rolled back or allow that tombstoned account to mutate. Preserve complete journal records through concurrent writers/crashes; reject corruption/incomplete intent safely. Cleanup receipts and jobs survive account removal; replay can rebuild them from the journal and restored source/cleanup/ownership metadata.

Before exposing a restored API or worker, replay the latest independently retained journal against the restored DB and private source store. Require the configured readable complete journal, remove every old account and its captured/restored original keys, drain durable cleanup, and verify no old owned rows/files remain. Never restore from an older journal packaged inside the DB backup. Verify with an actual synthetic backup/restore drill and preserve a later fresh account plus an unrelated account. Backup storage, production backup cadence and hosted restore operations remain D34; document the required recovery command without deploying.
