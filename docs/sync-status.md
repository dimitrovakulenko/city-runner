# Sources and foreground refresh (D19 / D25)

Scope: a useful web source/status flow for the implemented GPX/FIT pipeline. Garmin/Strava adapters and consent are D20–D23. They remain unavailable, with no connect/reconnect controls, fabricated sync date, available-history promise or provider credentials in this slice. Android/iOS execution belongs to the separate team.

## Owner status API

`GET /api/sync/status` requires the ordinary bearer session. No caller account ID or activity filters: this is account-wide retained history, independent of the selected map period. Return a typed response with:

- `change_token`: an opaque versioned token for committed owner state and shared geography state; never an account credential or private object key.
- `activity_count`, `oldest_activity_date` (oldest known valid recorded date, otherwise null), and `last_import_at` (latest current successful ingestion job's completion timestamp for a retained file, otherwise null). Matching/source updates cannot move that timestamp. Neither field establishes provider history availability or last provider sync.
- `files`: distinct live sources, split into GPX/FIT and queued/processing/imported/failed ingestion counts. The current revision's ingestion job is authoritative: exhausted/failed/cancelled jobs cannot appear queued merely because the source row was not updated. Missing current job state is unavailable, never successful. Batch replay duplicates are reported separately; they never inflate imported activities or source counts.
- `coverage`: counts of imported file sources whose matching is ready, pending, failed or unavailable without active complete geography. Every applicable active complete dataset must have current source-revision/run/job success before a source is ready. Failed current jobs override a stale queued/run state. Preserve safe failure and unknown states; ingestion success is not coverage success.
- `batches`: manifest-item counts for waiting, accepted, duplicate and deleted entries, plus stopped batches. Deleted items stay terminal. Waiting files are never automatically submitted or reimported.
- `providers`: Garmin and Strava capability entries explicitly marked unavailable, with a safe explanation that their adapters are not implemented. No secrets, provider subjects, cursors, files, raw GPS or internal job payloads are exposed.

Return `Cache-Control: no-store, private`. Accept an optional bounded `since` token (maximum 200 characters); if unchanged return 204 with no body. Authentication and the deletion journal are checked before this result. An ordinary GET always returns the full status. Read token and all aggregates in one read-only repeatable snapshot, with 1.5-second statement/work and bounded lock budgets. Queries aggregate indexed owner metadata; they must not load GPS arrays or scan node contributions. Safe 503 guidance covers budget exhaustion. This endpoint is PostgreSQL-only, like the matching/map APIs.

`GET /api/sync/failures?page=1&page_size=20`: owner-only stable source-ID ordering, maximum page size 20, typed page with total, items and current change token. Each item contains string `source_id`, file kind, nullable string activity ID, stage `import` or `coverage`, safe allowlisted error, and a retry action. Only current live GPX/FIT sources with a current failed ingestion or matching job appear. Never expose storage keys, provider IDs, timestamps invented as now, old revisions or another owner's data. This is a bounded failure page, not a history download.

Existing `POST /api/uploads/{id}/retry` remains ingestion retry. Add `POST /api/uploads/{id}/retry-coverage` returning 204 for a current imported file source: retry its failed current matching jobs for active complete datasets, at most 32 datasets per request. Already queued/running or successfully matched work is idempotent; no failed work is a no-op. Missing/other-owner/deleted source returns 404, un-ingested source 409, an excessive dataset count returns safe 409 before mutation. No new samples, source revision or coverage credit are created. Retain immutable originals and exact dedupe behavior.

Matching retry obtains the account guard before private locks, locks relevant current jobs in ascending ID order, then source/activity/run/summary in the existing worker/deletion order. Revalidate source ownership/revision, active dataset identity and job/run association after locking. Reset only failed/cancelled matching jobs and their current runs; clear expired leases, reset bounded attempts/backoff, refresh processing/pending summaries. Concurrent retry/delete/worker/requeue cannot resurrect deleted data, restore stale support or invalidate a live worker lease. No original upload is repeated.

## Change detection

Use a monotonic transactional owner revision and a monotonic shared geography revision. Account revision starts at zero; IDs/revisions remain strings at the API boundary. Changes to activities, live sources, manifests/items, ingestion/matching job state, current matching runs/summaries and manual labels advance the owner revision. Changes to dataset state/identity advance geography revision. New geography is immutable within a dataset version; replacement activation remains separately gated. Lease heartbeat-only updates and private-original cleanup do not trigger full map/history refresh.

Revision changes must commit or roll back with the underlying writes, survive API/worker restart and detect deletes or same-timestamp updates. Existing timestamps/maxima are insufficient. If database triggers are used, defer counter writes to transaction completion so they do not introduce an account-counter → job/source lock inversion. Collect all touched owners and lock/update their counters in deterministic owner-ID order: lease recovery can modify jobs across multiple accounts in one transaction, so merely deferring individual row events is insufficient. Exclude no-op row updates and cleanup-only jobs. Auth/session operations do not increment the data revision. Deleted accounts simply fail authentication; no status response resurrects them. Coalescing events is optional, not a new queue/framework.

## Browser behavior

Expose a Sources & sync screen: file/coverage/history status, oldest known date, last file import, paged failures with explicit retry and links to imports/activities, and unavailable cloud capabilities. Show waiting/reselection and stopped uploads distinctly from accepted jobs that continue on the server. Keep period filters out of account-wide status; labels must say file import, not cloud sync.

Poll lightweight status only while signed in, visible and online, at a minimum 2.5-second cadence. One status request/refresh cycle at a time, ten-second status timeout, generation/token/abort fencing on account replacement, hide and offline. Successful polling continues while eligible; bound consecutive failures to five with backoff and a visible Retry refresh action. Reconnect, visibility return and explicit retry resume polling. An explicit refresh during an active cycle is coalesced into the next eligible full read; its request cannot be cleared by the earlier cycle. The browser never starts or retries uploads as a consequence of status polling.

Unchanged tokens perform no expensive activity/map/city/import reads. Changed tokens refresh bounded current views using existing filters, search, dataset/city/street selection, detail and viewport. Preserve planner edits and selected coverage scope. Refresh the activity detail when processing changes; a selected activity deleted elsewhere clears safely. Retained pages may be refreshed within their existing bounded API pages; do not fetch an entire history. Capture the current account generation before refresh, and acknowledge a token only after its dependent refreshes succeed; an error allows retry of the same token. An earlier response cannot replace newer selections or a replacement account.

The first status read after activation/reconnect also refreshes dependent views: otherwise an import that finishes between initial view reads and the status baseline would be missed. Activity refresh retains at most five already-loaded pages, then leaves pagination available to continue. A superseded selection is a benign unacknowledged refresh; an actual view failure uses the error/backoff path. Offline/hidden transitions cancel status work, preserve permitted cached display with a stale label, and resume with a full status read when eligible. A dependent refresh already running must finish before another same-account cycle starts. Failed refresh is distinguishable from failed ingestion/matching.

## Future connection and provenance contract (D19)

Provider connection records will belong to an account and provider, with composite owner foreign keys from sources. Connecting a source does not create another application account or merge accounts by email. Credentials/refresh tokens are encrypted server-side using operator-held keys, never returned to clients/logs/exports. Cursor/watermark state stays server-side per connection and commits only with accepted work. Separate connection states: connected, syncing, rate-limited, reauth-required, disconnecting, disconnected. Unknown history availability and last success remain null until evidenced by the actual adapter.

Reconnect requires fresh verified consent for the same provider subject and owner; it replaces credentials and fences previous connection-generation jobs. A subject belonging to another account conflicts rather than moves implicitly. Disconnect first fences further work and revokes/removes credentials, then executes the approved provider-specific raw/derived/backup retention policy through durable cleanup. Existing file imports retain their independent provenance. Revocation is never presented as successful merely because a browser forgot a token. A retention outcome must be settled before enabling an adapter; this contract does not authorize permanent provider storage.

External activity identity is unique within its owned connection. Update/delete events advance source revision and fence leases before contributions change. New activity/event jobs retain priority 100 over history 10; backfill pagination/cursors must not starve new events. Reconciliation handles missed/out-of-order events and throttling without inventing progress or resetting completed backfill.

Exact same-file dedupe remains account + file kind + bytes. Provider identity/event replay is idempotent within its connection. Similar date/distance/geometry across sources is insufficient to merge or delete records. Preserve independent sources and count account node visits as their distinct union. Removing one source removes only its support; file provenance cannot authorize retaining data derived solely from a revoked provider. Cross-source workout grouping and provider-specific retention implementations remain D24 / real adapter acceptance.
