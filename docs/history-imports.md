# Full-history file imports

This web slice accepts loose GPX/FIT files, a selected folder or one ZIP. It reuses the existing private-file parsers, sources, jobs and 20-item import batches. Native folder/ZIP pickers and provider adapters remain separate.

## Bounds and local preparation

One history import contains 1–1,000 activity files, each from 1 byte to 10 MiB, with at most 256 MiB of activity bytes in total. A selected ZIP is at most 64 MiB and has at most 10,000 entries. Directories and unrelated entries are skipped without decompression; nested archives are not recursively opened. Reject unsafe absolute/traversal paths, symlinks and inconsistent container/path/offset metadata. For extracted GPX/FIT entries, reject encryption, unsupported compression, inconsistent local/central metadata, corrupt CRCs and actual output exceeding the per-file/total bounds. Skipped unrelated entries are not decompressed or CRC-verified. Bounds apply to actual decoded bytes as well as declared sizes. Enumerate and extract sequentially with cancellation; keep decoding off the main thread where the library supports it. Never write ZIP entries to disk or upload the archive itself. Only GPX/FIT bytes go through existing uploads.

Prepare all accepted files before manifest creation: validated basename/format/size and SHA-256 of their unchanged bytes. Folder-relative and archive paths are local-only and never persisted or sent to the backend. Reject an empty/oversized selection with actionable guidance before creating manifests; report skipped non-activity files. Exact duplicate basenames are allowed because reselection matches basename, format, size and hash, not picker order. Valid ZIPs containing corrupt GPX/FIT still receive the existing per-file parser errors after upload.

File handles and extracted bytes remain memory-only. Clear them and abort preparation on account/session change or cancellation; release completed selections. After reload, select the ZIP/folder/files again for an existing history import. Match only its awaiting items with the exact declared identity, across all child batches, and never create a new history implicitly. Deleted/accepted items are never submitted again. A selection can satisfy several identical-byte duplicate items safely. Local selection does not reopen a stopped history: explicitly resume it.

## Durable API and migration 0015

Add owner-scoped `import_histories` with ID, request UUID, manifest digest, sanitized label, open/stopped state and timestamps. Child `import_batches` gain nullable owner-qualified history ID and ordinal (0–49). Items gain nullable `expected_sha256` and `expected_size`; ordinary batches remain compatible and retain their original 20-file limit. No automatic migration/backfill of existing batches. Owner export includes histories, batch relationships and declared item identity; account deletion cascades all of it. Extend sync revision tracking for committed history state changes.

- `POST /api/import-histories`: UUID `request_id`, basename `label` (1–200 characters), and 1–1,000 `files` with basename `name`, `format` (`gpx`/`fit`), integer `size` (1 byte–10 MiB), lowercase 64-hex `sha256`. Validate aggregate size ≤256 MiB. Atomically create the parent and all ordered child manifests, each at most 20 items. Create no source/job until an upload is accepted. Exact request replay returns the same parent/batches; a changed manifest on that UUID returns 409. Bound request body to 4 MiB before JSON parsing; oversized body returns 413 without rows. Return 201 and a typed history summary.
- `GET /api/import-histories?page=1&page_size=20`: summaries ordered by created_at then ID descending; page size 1–20. `GET /api/import-histories/{id}` returns one summary. Summary fields: string `id`, `label`, `state`, `created_at`, integer `file_count`, ordered string `batch_ids` (≤50), the existing six item `counts`, and accepted `duplicate_count`. Counts use current source/job truth exactly as batch detail, including terminal deleted items, without reading GPS/originals. Owner-only/missing IDs return 404.
- `GET /api/import-histories/{id}/batches?page=1&page_size=20`: existing typed batch pages ordered by history ordinal, page size 1–20. Batch responses gain optional nullable `history_id`; item responses gain optional nullable `expected_sha256`/`expected_size`. Legacy list returns standalone batches only, while explicitly addressed owned child detail/upload/retry endpoints remain usable. All IDs preserve decimal-string BIGINT handling.
- `POST /api/import-histories/{id}/stop` and `/resume`: 204, atomically set parent and all children stopped/open. Stop pauses unsubmitted items; the current upload may settle if accepted before the stop commits. Accepted jobs continue. Resume never changes terminal/deleted items or job state. Child resume cannot bypass a stopped parent (409).

Every child upload verifies actual size/hash against declared identity before writing originals or pinning a source; mismatch returns 409 with the item awaiting/unpinned. Ordinary uploads retain existing behavior. Owner guard precedes parent, batch, item and existing job/source locks. For history children, read the owner-qualified parent hint without row locking, then lock parent before child; stop/resume use the same parent-first order and ascending child IDs. Revalidate parent open state at final acceptance. Preserve correction rollback/retry, account isolation, lease/revision fencing, recording deletion watermarks, exact same-file dedupe and equivalent recording grouping. Declared hashes never authorize importing a deleted historical item.

## Shared client and browser behavior

Generate client types from the implemented backend before wiring the new API/store. Extend the existing shared import store and its single-upload ownership/queue rather than adding a second uploading pipeline. A history creation is serialized; all child manifests are durable before starting uploads. Upload one file at a time across chunks, stop scheduling on upload failure, and retain files for explicit retry. Parent stop immediately prevents scheduling later child files locally and commits the durable stop. Resume queues only matched awaiting items; accepted files remain server work. Account/request generations fence list/detail/preparation/create/mutation/upload callbacks. Lost creation responses retry the same request UUID instead of silently creating another parent.

History cards show overall uploaded/imported/processing/waiting/failed/deleted and duplicate progress, stop/resume/retry, and ZIP/folder/file reselection. Show bounded child/item pages, preserving the existing per-file errors, processing retry and activity links. Ordinary ≤20-file imports and native APIs remain usable. Reload loads parent summaries and durable children; handle/file reselection is explicit. Status polling remains foreground-only and bounded; history progress comes from server summaries, not only the visible child page. Backend/browser restart cannot lose manifests or implicitly restart stopped uploading.

## Verification

Use synthetic files only. Review the contract, backend and shared client independently. Verify atomic replay/conflict/rollback, bounds, owner isolation/export/deletion, expected-byte mismatch, stop racing acceptance across chunk boundaries, current-job aggregate truth, terminal deleted items, restart and revision/lease compatibility on disposable PostGIS. Verify ZIP CRC/truncation/encryption/path/symlink/entry-count/output bounds, folder filtering and same-basename/hash reselection without uploading bad archives. Shared tests cover sequential cross-batch uploads, stop/resume/failure/retry, uncertain creation response, reload/reselection and account races. Actual production Chrome uses >20 files and a synthetic ZIP/folder, demonstrates overall progress, stop/reload/reselect/resume and deletion without reimport; compare uploaded originals and GPS to the fixture bytes. Run backend units/PostGIS, generated types, mobile tests/typecheck, web tests/build, both JS exports, then reviewed commits to main, push and verify hosted CI. Native execution, provider access, deployment, SDK installation and private PoC data remain outside this slice.

Browser ZIP decoding uses pinned `@zip.js/zip.js` 2.23.0 (BSD-3-Clause). Its [Blob reader and incremental entry enumeration](https://gildas-lormeau.github.io/zip.js/api/classes/ZipReader.html) and [CRC, metadata and cancellation options](https://gildas-lormeau.github.io/zip.js/api/interfaces/ZipReaderOptions.html) support bounded preparation; application output limits remain enforced independently in the destination stream.
