# Activity file import

`POST /api/uploads` accepts one private GPX or FIT activity file (10 MiB maximum) in multipart field `file`. It returns the existing upload/source and job response. Exact duplicates are scoped to the account and file kind, so identical bytes submitted as GPX and FIT remain separate sources. Original files are written under random private `.gpx` or `.fit` keys; existing `.gpx` keys remain readable.

GPX parsing preserves track segments and aligned timestamps. FIT parsing uses `fitdecode` 0.11.0 with strict message and CRC checks, limits total data/definition messages to 200,000 and record messages to 100,000, excludes developer-defined fields from native GPS/time fields, converts raw latitude/longitude semicircles to degrees, and retains absolute FIT timestamps in UTC. Relative timestamp values without an absolute epoch remain null. Timer stop/start events and records without usable coordinates split the output segments; records while the timer is stopped are ignored. Missing time and summary metadata remain null or `unknown`. Activity FIT files without usable GPS samples fail as `fit_no_track_points`; no activity or coverage is fabricated. Course/workout FIT files, malformed/truncated/checksum-invalid files, and concatenated FIT streams fail with bounded error codes.

For backward compatibility, `.fit` filenames select FIT parsing and `.gpx` filenames select GPX parsing. Other or extensionless filenames select FIT only when the payload has the `.FIT` magic at bytes 8–11; otherwise they select GPX. Multipart content type is not trusted. Both parsers feed the same existing ingestion and coverage jobs.

`fitdecode` is MIT-licensed and available from [PyPI](https://pypi.org/project/fitdecode/0.11.0/); its reader exposes decoded data messages and optional CRC matching in the [maintainer documentation](https://github.com/polyvertex/fitdecode). Synthetic FIT fixtures exercise coordinates, segmentation, timer pauses, no-GPS, record/message limits, file types, truncation, CRC, concatenated-stream rejection, big-endian fields, and compressed timestamp rollover. A developer-field collision check ensures custom fields cannot impersonate native coordinates. No real activity file is included in tests.

## Durable bulk imports

`POST /api/import-batches` records an ordered manifest of 1–20 files and a client UUID `request_id`. Replaying the same request returns the same batch; changing its manifest returns 409. The manifest keeps sanitized basenames and formats, never device paths. Owner-scoped list/detail endpoints provide per-file status, source/activity IDs, duplicate flags, safe errors and six status counts. Lists are bounded and paginated. See the [D18 contract](backend-contract.md#fit-and-resumable-batches-d18--migration-0009).

Upload each awaiting item's bytes to `POST /api/import-batches/{batch_id}/items/{item_id}/upload`, using its returned string ID. The server atomically attaches the source and durable job before acknowledging it. Identical content replays safely; different bytes for an attached item return 409. Dedupe remains account- and format-scoped. The [mobile importer](mobile-imports.md) submits files sequentially and distinguishes uploading from server processing.

`POST /api/import-batches/{batch_id}/stop` pauses unsubmitted items. Accepted jobs continue processing; an upload still being read must recheck the batch state before acceptance. `resume` reopens submission. Manifests survive API/app restarts; device file handles do not, so awaiting files require explicit reselection after app restart. Deleted items remain terminal across stop, resume and retry. Explicitly creating a new manifest or direct upload is a separate user-requested import.

`POST /api/uploads/{source_id}/retry` requeues only a failed ingestion source without a completed activity. It increments the source revision and creates a fresh job atomically; repeated calls while queued/running are idempotent. Job-before-source locks, READ COMMITTED revalidation and revision/lease checks fence concurrent retry, deletion and stale workers. Private blobs are cleaned up after duplicate or rolled-back attachment; durable deletion cleanup remains unchanged.

Verification uses synthetic files only: 31 backend unit tests and 62 disposable PostGIS tests passed, including concurrent upload/retry/deletion, rollback/commit failure, stop during upload, restart recovery, account isolation and GPX compatibility. Actual HTTP plus worker CLI verified FIT/GPX imports, duplicates, pause/resume, expired-lease recovery, API restart, safe corrupt-file failure, retry and terminal deletion. Safari Swagger verified unauthenticated 401 and authenticated persisted per-file states/counts. Native picker and device acceptance remain blocked by missing tooling.
