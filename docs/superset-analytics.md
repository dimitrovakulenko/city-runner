# Superset personal analytics implementation plan

Planned 14 October 2026; owner-selected Superset, no runtime or integration implemented. Requirement CR-23, work package T23, tasks D43–D47. Web first; geography expansion, provider registrations, deployment and native device work remain separate. This document plans the work, not authorization to install or deploy it now.

## User experience

Add an **Insights** entry to City Runner. Offer recommended boards immediately, with **Make my own copy** and **New board**. Users can choose chart types, metrics, dimensions, date ranges, city/activity/source filters, grouping and ordering; add/remove/resize/rearrange charts; save queries, charts and boards; rename, duplicate and delete their own objects. Advanced users can write read-only SQL against their permitted analytics datasets and save the result as a chart dataset. Nontechnical users use Superset Explore. Remember the user's default board across sessions/devices.

Recommendations are templates, not fixed layouts. Updating a template never overwrites a user's copy. Boards, queries, chart definitions and results stay private to their account. No public publishing or cross-account sharing in this slice. “Full flexibility” means authoring over the available personal datasets, not changing application completion rules, managing database connections, or executing Python, shell or server-side templates. SQL is the initial code language; additional languages and custom visualization plugins need a later demonstrated use case.

| Starter board | Initial charts | Suggested controls |
| --- | --- | --- |
| Exploration | Retained-history coverage growth, newly visited GPS nodes, streets advanced/completed, city progress table | City/dataset, date range, normal/strict rule |
| Activity | Activity count, recorded distance/time, activity-type breakdown, weekly/monthly trends | Date range, activity type, permitted source |
| Next streets | Current city completion, remaining GPS nodes, nearly-complete street table | City/dataset, normal/strict rule, completion range |

Provide sample SQL and plain field descriptions, units and metric definitions. Link city/street/activity identifiers back to the existing explorer and map through owner-checked routes. A synchronized custom map widget is not required initially: Superset authoring/dashboard support and useful explorer links are the acceptance target. Missing metadata, unfinished matching and limited history must remain visible.

## Architecture and privacy boundaries

Reuse Superset's SQL Lab, Explore and dashboard authoring UI. Run a pinned, supported Superset release as a separate service with its own metadata database and explicitly required cache/worker services. Reuse existing PostgreSQL/PostGIS data through a bounded read-only analytics interface; do not introduce another geography index or duplicate raw GPS history. Choose live protected views versus a separate projected analytics database at D43 based on measured query load and enforceable isolation.

The standard [embedded SDK](https://github.com/apache/superset/blob/master/superset-embedded-sdk/README.md) supplies dashboard viewing, not our complete authenticated authoring journey. D43 must prove a City Runner identity handoff into the full UI, private object permissions, session expiry/logout/account replacement, and private saved-query/result access on an exact released version. Decide between a proxied full UI and a separate authenticated analytics origin from that evidence. Do not promise a seamless editable iframe before checking cookies, CSP, CSRF and navigation. Reuse existing City Runner authentication; do not require users to register another account. An integration-specific security-manager adapter is acceptable only if stock permissions cannot meet the contract; keep any changes narrow and upgrade-testable.

Enforce data ownership at the database boundary for every execution path, including SQL Lab, virtual datasets, samples, exports and asynchronous queries. Superset filters or injected WHERE clauses are defense in depth, not the sole boundary. A shared database credential plus an account ID users can change with SQL/session settings is unacceptable. D43 first tests dedicated read-only account roles/connections with immutable account-bound grants or policies; it must prove that users cannot switch identities, reach another connection, or call privileged functions. Measure connection/role provisioning overhead before choosing this as the production design. If another execution design is needed, independently review it before implementation. A failure here blocks customer authoring; it cannot be replaced by admin-only analytics and called complete.

Restrict the queryable catalog to documented analytics fields. Exclude auth/provider credentials, login identities, raw tracks/coordinates, original files, filesystem locations, support reports and deletion-journal contents. Owner-scoped activity statistics, city/street identities and live GPS coverage aggregates are initially sufficient. Disable user-managed connections, uploads, public links, server-side template execution and unneeded outbound integrations. Privileged configuration remains operator-only. [Superset security guidance](https://superset.apache.org/admin-docs/security/) explicitly requires database-level protections; its SQL safeguards are not a database firewall.

Bind metadata ownership independently of dataset visibility: users must not discover another user's board names, SQL, chart definitions, query history, jobs, downloaded results or permalinks. Template definitions contain no user values. Cache/result keys include authenticated owner, query parameters, dataset/version/rule and data revision. Returning a saved result rechecks current access and revision; expired/deleted accounts cannot use a copied URL or old job handle. Avoid credentials or private result values in operational logs.

## Data and metric contract to settle before implementation

| Dataset | Row grain and semantics |
| --- | --- |
| Activities | One retained logical activity, not one uploaded source. Recorded date/type/distance/time use [existing statistics](activity-statistics.md), with nulls preserved; source filtering uses distinct activity semantics. No duplicate totals from GPX/FIT imports of the same recording. |
| City/street progress | One owner + OSM dataset + street/current rule. Eligible-node denominator, GPS visits and manual status are separate. Current dataset and coverage revision/readiness are explicit. No exact street-length claim. |
| Exploration history | One retained activity + selected dataset/rule with chronological attribution matching [activity impact](activity-impact.md). New nodes are a distinct union; completed streets cross the same normal/strict thresholds. Same-day ties are approximate. |

Settle date boundaries/timezone, source filtering, grain, allowed joins, units, readiness and bounds in a reviewed backend contract. Period-supported GPS coverage and **new during the period** are different measures: new coverage compares against earlier retained history, while period-supported coverage is the distinct union supported by selected activities. Summing per-activity advanced streets does not give distinct advanced streets in a period. Label measures accordingly. The existing 10,000-activity history limit and unknown-date/missing-provenance states remain explicit until a separately reviewed scalable implementation replaces them.

Growth is a reconstruction from currently retained, successfully matched activities against one selected OSM dataset, not an immutable record of what the user saw on a past date. Backdated imports, deletions, source edits and dataset changes can alter it. Do not join different OSM versions into one unexplained completion curve. Manual completion never adds GPS history credit. Pending/failed/unsupported geography is unavailable, not zero or complete. Thresholds, original samples, gaps and lease/revision fencing remain owned by the existing backend.

Any derived projection needs bounded idempotent refresh, exact owner/source/dataset revision checks and current source/job/run validity before publication. Charts revalidate on import, correction, deletion and dataset changes. Stale results are withheld or explicitly marked stale; deleted data is never served from a cache. Source/account deletion must fence in-flight queries, invalidate private results and remove analytics metadata under an independently reviewed durable cleanup/restore contract. Extend the existing account export/deletion workflow to include personal board/chart/query definitions and their ownership mappings; never restore a deleted account from Superset metadata backups. Unapproved provider data remains excluded from analytics, including derived values and caches.
