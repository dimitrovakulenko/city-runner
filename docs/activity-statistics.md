# Recorded activity statistics (T05)

Scope: distance, recorded duration and recorded average pace on the existing activity list/detail. Compute metadata for new GPX/FIT ingestion and explicitly backfill existing stored activity tracks. No dashboards, totals, provider adapters, inferred moving time or native execution.

## Metrics

Add nullable `distance_m`, `duration_s` and `pace_s_per_km` to `ActivitySummary` and inherited `ActivityDetail`. Responses always include these fields; schema defaults of null preserve older fixtures/clients. Store the three values and an internal algorithm version on `activities`; lists select metadata only and never load GPS arrays. Unknown/unprocessed legacy statistics are null, never fabricated zeroes. The algorithm version distinguishes unprocessed rows from processed-but-unavailable rows.

Version 1 uses original normalized `tracks` and point-aligned `timestamps` from the existing GPX/FIT parsers. It does not use FIT session/device distance or timer totals: identical recorded segments must produce identical metrics in both formats and in backfill. Never modify original coordinates, timestamps, segmentation, source revisions, jobs or coverage support.

- `distance_m`: sum the haversine distance between adjacent coordinates **within each segment**, using the fixed spherical approximation radius 6,371,000 m and shortest longitude difference. Clamp floating-point haversine input to [0,1]. Never connect separate segments, FIT pause boundaries or missing-position gaps. At least one valid adjacent edge is required; otherwise null. A valid stationary recording has distance zero. This is recorded GPS distance, not a guarantee of full workout distance or survey accuracy.
- `duration_s`: sum UTC-normalized positive timestamp differences between adjacent points within each segment. Every GPS point must have a valid explicitly zoned full timestamp and the timestamp shape must match tracks. Times must increase strictly within each segment; a segment may start at the previous segment's ending time but cannot overlap or run backwards. Missing, invalid, naive, duplicate within-segment or nonmonotonic times make the entire duration null; never sum only the known intervals. With no adjacent edges, duration is null. Inter-segment time is excluded. Stops inside a continuous GPX segment remain included; no moving-time inference is made.
- `pace_s_per_km`: `duration_s * 1000 / distance_m`, only when both values are known and strictly positive; otherwise null. No infinity, NaN, negative values or division by zero may be stored/exposed.

Validate legacy inputs before calculating: coordinates must be finite numeric [longitude,latitude] pairs within [-180,180]/[-90,90], with booleans rejected. Malformed coordinates/track shape, more than 100,000 points or more than 100,000 segments produce unavailable statistics safely. Invalid timing leaves valid distance available. Use bounded linear work and retain full calculation precision; round only presentation. Existing parser corruption/no-GPS errors remain unchanged.

## Persistence, migration and backfill

Apply a new additive migration after `0012_sync_status`. Existing rows start with null metrics and version zero; do not scan GPS or read private originals inside the migration. New upload statistics commit with the existing lease/source-revision-fenced activity insertion. Retry/duplicates cannot create additional activities or recompute a stale/deleted source.

Provide an explicit bounded operator backfill command scoped to a required account ID, with optional signed-BIGINT keyset `after_id`, a maximum of 100 activities per invocation and metadata selection batches no larger than 20. An omitted cursor includes negative legacy IDs; candidate selection filters unprocessed versions so rerunning without a cursor advances past committed work. Calculate from stored tracks/timestamps only, one activity at a time under an account guard and owned activity row lock, with bounded lock waits. Read and write the same locked row, recheck algorithm version/ownership, skip already processed rows, and mark safely unavailable records processed. Each activity commits independently; interruption/rerun resumes using the persisted version. Do not automatically run this command on startup or during GET requests, and never recreate deleted activities/accounts/sources. Concurrent ingestion, deletion, coverage processing or repeated backfill must preserve their existing lock order/fences and GPS support.

Statistics changes advance the existing transactional account sync revision. Extend the activity revision collector in the new migration; changing metrics/version triggers refresh, unchanged values do not. Account archives include these metadata/version fields through the existing owner-only bounded allowlist. Account deletion removes them with the activity. SQLite API test schemas need equivalent nullable columns; preserve existing API filtering, paging and ID behavior.

## Client and web display

Generate mobile API types from the implemented backend before wiring UI. Share one small formatting helper between the browser and native activity list/detail. Display GPS distance in kilometres, recorded time as m:ss or h:mm:ss and pace as m:ss/km, rounding seconds before splitting minutes so rollover is correct. Nonfinite/negative/absent values display unknown; stationary distance zero remains a legitimate zero, while pace remains unknown. Very small positive values must not be presented as exact zero.

Show the three metrics in activity detail and a compact list summary. Explain that these use recorded GPS segments, time excludes inter-segment gaps and unmarked stops remain included. Keep filters, selected activity, route drafts and account fences intact. Backfill/new imports become visible through existing source-status refresh. Do not derive metrics from clipped map geometry or transfer entire histories to the client.
